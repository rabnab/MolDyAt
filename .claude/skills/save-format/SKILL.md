# Save Format Contract

Saves are pretty-printed JSON files written by `SaveStore` (`crates/thermo_physics/src/application/persistence/`): Ctrl+S writes `world_YYYYMMDD_HHMMSS.json` into the save directory (`--save-dir`, default `saves/`), Ctrl+O and `--load` read them, `--save-setup` writes the prepared world of a headless run. Plan decision: **old saves keep loading** (`docs/plan/refactoring-plan.md` §6).

## Files
| File | Role |
|---|---|
| `format.rs` | `WorldFile`, its data structs (`BallData`, and in the `operators` list `OperatorData`: `WallChainData` with `ChainPieceData` / `JointData`, `SourceSphereData`, `ThermostatData`), `WORLD_FILE_VERSION`, `validate()`, `to_json` / `from_json`, `sim_config()` (the saved `SimConfig`, or the defaults for older files) |
| `migrate.rs` | `parse()` (version first, fast path for current files), the `MIGRATIONS` chain and `take_field` for writing migrations |
| `convert.rs` | live world ⇄ file (`WorldFile::capture(&MainContent)`, `TryFrom<&WorldFile> for SimulationWorld`, `From` impls for each `*Data` struct) |
| `store.rs` | save directory, file names, atomic write (temp file, then rename), `latest()` |
| `mod.rs` | `MainContent::load_world`: resolve, read, validate, build, then swap in |
| `tests/` | `format.rs`, `migrate.rs`, `newer_files.rs`, `roundtrip.rs`, `store.rs`, `reference_saves.rs` (one fixture per format version in `tests/fixtures/`) |

## Rules
- **The file has its own types.** Every saved object is written through a dedicated `*Data` struct, not its runtime type (balls, walls, valves, wall chains, source spheres, thermostats; #270).
- **One operator list (#274, v3).** `WorldFile::operators` holds every operator as `{"<kind>": {...}}` (`OperatorData`), grouped by kind in capture order; `wall_chains()`, `source_spheres()` and `thermostats()` iterate one kind. A wall chain owns its pieces (each with the segment's `id`, `start`, `end`, `thickness`) and its valve joints (`valve_id`, `is_closed`): segments and valves have no lists of their own, so no cross-references between operators are left to check, only that piece, valve and chain ids are unique. Restoring splits them back into the world's line segment and valve collections, sorted by id. An entry of a kind this build does not know is skipped and reported as `operators[i].<kind>` (see "Newer files"); an entry needs exactly one key. The simulation types (`SimLineSegment`, `ValveSegment`, `WallChain`, `Joint`, ...) do not derive serde, so refactoring them cannot change the file; their conversion lives in `convert.rs`. Keep it that way for new state: runtime-only fields (caches, neighbour lists, chain scratch) must not leak into the file.
- **Built-in species are part of the format.** Since v2 a ball stores only its species name (`species`, `ball_species`); mass, `σ` and `ε` come from the file's species table at load time: the `[[species]]` list of its `config` if it has one (#237, `SimConfig::species_table`, the whole table, validated in `validate()`), otherwise `SpeciesTable::builtin()`. `validate()` returns that table with the pair overrides (`ResolvedSpecies`), and the world is built from it (`SimulationWorld::with_resolved`) without resolving them again. Conversion (`convert.rs`) looks names up in the world's table (`SimulationWorld::species()`), never in `builtin()`, and `load_world` hands the loaded table to the ball factory (`BallFactory::use_species`, which resets the species of new balls if the table differs). Renaming a built-in species makes every save that uses it fail to load; changing its mass, `σ` or `ε` silently loads old saves with different physics. Either is a breaking change: bump `WORLD_FILE_VERSION` and add a migration, or add a new species instead of changing an existing one. `builtin_table_is_pinned` (`objects2d/ball_impl/species.rs`) pins the whole table; update it only together with one of those.
- **The simulation config is part of the format.** `WorldFile::config` (`Option<SimConfig>`, `application/sim_config/`, #231) is written by every save and restored on load; files without it run with `SimConfig::default()`. So its key names and meanings are format, and so are its defaults: changing a default changes how every save without a config runs, which is a breaking change (bump the version and write the old value into those files in a migration). A new key gets a default equal to today's behaviour. `SimConfig` rejects unknown keys (`deny_unknown_fields`), so every config key is a format contract: adding a key makes the new saves unreadable for older builds of the same format version (`WorldFile::from_json` adds a "probably written by a newer MolDyAt build" hint to the error). That is intended (#273): a dropped config key would change the physics. A new key that changes results also bumps the version (see "Newer files" below), so older builds report a newer version instead of an unknown key. An optional list key keeps saves that do not use it readable: `potential.pair_override` (#235) is `skip_serializing_if = "Vec::is_empty"`, so only saves with overrides carry it. Builds from before #231 ignore `config` and run such saves with the defaults. Every key has a range (`MIN_*` / `MAX_*` in `sim_config/mod.rs`); a new key gets one. The top-level `time_step` must lie in `MIN_TIME_STEP..=MAX_TIME_STEP` and equal `config.integration.time_step` (`validate()`).
- **Two value types are part of the format.** `Vec2D` (`{x, y}`) and `Rect` (`{x, y, w, h}`) are written as they are: their layout is stable and every file type uses them. Renaming, adding or removing one of their fields changes the save format, even if the change looks unrelated; treat it as a format change. `wall_layout_is_unchanged_by_the_file_types` (`tests/reference_saves.rs`) checks that the walls' JSON in the current reference save survives a load and a save unchanged.
- **Validate before touching the world.** `from_json` runs `validate()`; `load_world` builds the new `SimulationWorld` completely before replacing the running one, so a bad file leaves the simulation untouched (`invalid_file_leaves_the_running_world_untouched`). Every new field gets a check in `validate()`: finite numbers, ranges matching the runtime limits (reuse the `MIN_*` / `MAX_*` constants), unique ids below `MAX_ID`, references that resolve (valve → wall, chain → pieces).
- **Ids continue.** After a load, operator id counters (`OperatorIdCounter::after`) and the ball factory continue after the highest restored id.
- **Index contract.** The loaded world rebuilds the cell grid and neighbour lists from scratch (`collect_neighbours_by_cell`); never restore stored indices.

## Changing the format
Loading (`migrate::parse`, #272) reads the version first: a current-version file is deserialized directly (the `Value` path is many times slower for large saves), an older one is parsed to `serde_json::Value`, upgraded through the `MIGRATIONS` chain, logged, then deserialized. Both are validated. Files without a version, version 0 or newer than the build are rejected.

**Newer files (#273).** A file from a newer build:
- with a newer version: rejected ("version N is newer than this build supports (up to M)");
- with unknown keys in `config`: rejected, with the "probably written by a newer MolDyAt build" hint;
- with unknown fields anywhere else: loaded. `migrate::parse` wraps both deserialization paths in `serde_ignored` and returns the skipped paths (`balls[3].charge`, `pistons`), grouped with `*` for list indices when a field repeats (`balls[*].label (100000 entries)`, so a field on every ball stays one entry); `load_world` logs them as one warning (at most 20 named, then "and N more") and returns them in `LoadedWorld::ignored_fields`, and the load message counts them. Saving that world again drops them.

So **an addition that changes results bumps the version**, even when it is additive for older files (a new operator kind, a new physics field or config key): add the `#[serde(default)]` as in step 1 *and* a migration that only updates the number, so older builds refuse the file clearly instead of running it with different physics. Only additions that change no results (display, metadata) keep the version. `serde_ignored` cannot see into serde's internally tagged or flattened types, which buffer their fields: a file type must not use them (`JointData` reads its `kind` through a plain `RawJoint` struct, and `OperatorData` is keyed by its kind for this); `unknown_fields_outside_config_are_skipped_and_named` (`tests/newer_files.rs`) covers every nesting kind.
1. Decide whether the change is compatible (#271).
   - **Additive, no migration (and keep the version unless it changes results, see above):** a new field gets `#[serde(default)]` or `#[serde(default = "fn_name")]` with a default that reproduces the behaviour of older builds (the value that used to be hard-coded); a new top-level list is `#[serde(default)] Vec<…>`; a new operator kind is a new `OperatorData` variant (older files simply have none of it). `validate()` must accept the default. This applies to every saved type, including the shared ones below.
   - **Breaking, bump the version and add a migration:** renaming or removing a field, changing its type, unit or meaning, or changing a default that older files rely on. `#[serde(default)]` would load such files silently with wrong values.
   - `old_saves_load_into_a_file_type_with_new_fields` (`tests/reference_saves.rs`) shows the additive mechanism on every reference save; a real new field gets its own check that an older fixture loads with the default.
2. For an incompatible change: bump `WORLD_FILE_VERSION` to `N + 1` and add `migrate_vN_to_vN+1(&mut Value)` to `MIGRATIONS` in `persistence/migrate.rs` (the chain test checks that entry `i` upgrades version `i + 1`). A migration must not panic on unexpected input: use `take_field` and return `invalid(..)` for missing or mistyped fields, never `unwrap` or index. Remove the `expect(dead_code)` on `take_field` with the first real migration. Saving always writes the newest version.
3. Add the new version's reference save to `persistence/tests/fixtures/` (written by the new build) with its checks in `FIXTURES` (`tests/reference_saves.rs`). Existing fixtures are never edited or regenerated; they must keep loading through the migration.
4. Examples: v1 → v2 (#234, `migrate_v1_to_v2`) turned each ball's `size_idx` and each source sphere's `ball_size_idx` into the name of a built-in species (`species`, `ball_species`); the size class species keep the old equilibrium distances. v2 → v3 (#274, `migrate_v2_to_v3`) moved the five operator lists into `operators`, each chain taking in its segments and valves; segments and valves no chain refers to had no effect and are dropped with a warning. `v2_upgrades_to_the_v3_reference_save` pins it against the v3 fixture.

## Tests and checks
- Round trip: save, load, compare (`world_survives_a_save_and_load`); add the new state to `busy_world()` in `tests/roundtrip.rs` so it is covered.
- Validation: one test per rejected case (non-finite, out of range, duplicate id, dangling reference).
- Every reference save loads: `cargo test -p thermo_physics reference_saves` (#269).
- `cargo test -p thermo_physics persistence`, then `cargo fmt` and `cargo clippy --workspace -- -D warnings`.
- `scripts/headless_perf.sh` caches worlds saved with `--save-setup` in `target/perf-worlds/`; after a format change, delete that cache.
- Update `README.md` (save/load section) if user-visible behaviour changes.
